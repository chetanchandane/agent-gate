What this is

agent-gate is a regression gate for changes to an LLM agent's behavior. The agent is a fictional home services booking and dispatch assistant (HVAC, plumbing, electrical). Its behavior lives in versioned plain text policy files, and those files are the only thing that changes between versions.

An improver LLM reads the current version's failures and proposes edits. A deterministic gate then accepts an edit only if it clearly improves a dev set, causes no confirmed regression in a protected safeguard set, holds on a hidden holdout set, and stays within cost and latency budgets. Every decision is written to disk with the numbers behind it. The improver never sees the holdout set.

This page is one run's evidence. Section 1 compares the first policy to the latest on a frozen benchmark. Section 3, the rejected candidates table, is the point of the project: it shows the gate turning away bad edits, both ones the improver proposed and three deliberately bad policies written by hand to test it, with the exact rules they failed and the cases they regressed. Numbers are real and vary between runs because the model is non deterministic; the intervals and sample sizes are shown throughout.

7. Limitations

  • Small sample sizes: a few dozen cases per set, so rates carry wide intervals.
  • A single domain (home services dispatch) and mock tools, not a real backend.
  • The LLM judge is used only for tone, and only when deterministic checks pass.
  • The adversarial candidates were written by hand to test the gate, not proposed.
  • Results vary between runs because the agent and judge are non deterministic.
